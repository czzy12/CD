# StatementMetadata 覆盖审计 v1

> 审计日期：2026-07-27
> 范围：`pipeline.py` 的 58 个解析入口、当前解析器实现，以及本轮可读取的练习样本。静态存在容器不等于真实版式已可靠发现账户。

## 结论

- 当前有 9 个解析器路径返回 `TransactionList + StatementMetadata`：`abc`、`abc_corp`、`ccb`、`ccb_corp`、`citic`、`fudian`、`icbc`、`icbc_corp`、`spdb`。
- 本轮将工行对公企业存款对账单归入“原件明确但未映射”并完成补齐：首页唯一 `户名 / 账号` 且账号规范化后为 12 至 32 位数字时才写入元数据。
- 建行对公当前练习固定版式已受限映射：仅第 1 页唯一 `本方户名`，且每页唯一交易表首列 `账号`归一后为同一完整账号时写入元数据；不得拼接、猜测或接受掩码、多值、缺列和跨页不一致。
- 微信、支付宝不提供完整银行账户抬头，属于“原件本身不可用”；不因姓名创建银行账户映射。
- 其余 49 个入口尚无同版式原件证据可完成三类判定，记录为“待原件核验”，不把静态缺少元数据等同于解析缺陷或原件不可用。

## 分类与处理

| 分类 | 解析器 / 样本证据 | 处理 |
| --- | --- | --- |
| 已支持 | `abc`、`icbc` 个人固定版式；`icbc_corp` 企业存款对账单；以及 `abc_corp`、`ccb`、`citic`、`fudian`、`spdb`、`ccb_corp` 的既有路径 | 保持逐版式规则；仅完整、唯一、带标签的户名和账号可进入案件账户发现。 |
| 原件明确但未映射 | `icbc_corp` 企业存款对账单：首页 `户名 / 账号` | 本轮已实现并以真实样本验收。 |
| 已支持 | `ccb_corp` 当前练习固定版式：第 1 页唯一 `本方户名` 和每页交易表首列 `账号` | 仅所有页账号归一后唯一、完整且跨页一致时写入；任一页缺列、多值、掩码或异常即整体为空。 |
| 原件本身不可用 | 微信、支付宝 | 可保留文件身份文字，不创建银行账户映射。 |
| 待原件核验 | 其余没有同版式可核验原件的解析入口 | 取得原件后再归入前三类之一；不得按银行名称或相似版式推断。 |

## 第二个 v1D 案例筛选

- 工行对公练习目录的四份银行流水均发现同一可靠账户；交易侧有完整对手账号，但没有第二个可靠抬头账户，因此不构成双账户案例。
- 建行个人与建行对公组合可由同一案例目录的只读扫描器筛选：它只收集可靠抬头账户和双方互相完整可靠对手账号覆盖，生成待人工 `account_ref` 角色确认的清单；未确认前不运行 v1D。
- 当前练习样本未找到第二个可复验案例。该结果仅表示样本与前置条件不足，不放宽账户、来源文件、日期、金额或方向规则。

## 下一窗口入口

1. 使用 `tools/scan_case_account_candidates.py` 对指定案例目录生成只读候选清单；每个 PDF 独立超时，且输出格式、解析或可靠字段不可用原因。历史样本库仅可作版式/字段筛选。
2. 由人工按清单中的 `account_ref` 确认角色；文件夹本身不代表账户归属。
3. 仅在确认后运行既有 v1D，并分别报告唯一配对、单边、歧义和不可用原因。
