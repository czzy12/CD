## 2026-07-27 微信首页身份元数据与真实双源验收

### 实现与边界

- 微信解析器仅读取第 1 页明确的 `兹证明 / 居民身份证或身份证号 / 微信号`标签。姓名、完整身份证号和微信号均唯一时才写入来源元数据；掩码、缺失、格式不完整或多候选均拒绝。该读取不扫描交易页，也不把微信号伪装为银行账户。
- 案件发现将合格微信来源写入独立 `payment_sources`，再生成 `confirmed_owned_payment_sources`；身份三要素仅供上下文校验，标准结果 JSON 不回显。
- 微信扣款观察新增专用 `reliable_header_bank_accounts` 输入，来自可靠完整银行抬头及其来源文件映射。它只服务于“尾号唯一 + 同日精确同额 + 财付通/微信支付文字 + 商户组成部分”的关联，不改变 v1C/v1D 的已确认账户、完整对手账号或人工角色确认门槛。
- 微信交易方式文字层可将卡种拆成“储 蓄卡 / 信 用卡 / 银 行卡”；仅对此明确标签容许字间空格，其他文字不做补全。

### 真实原件验收

- 对现有练习材料中 16 份微信原件做首页预检，均可得到完整身份三要素；这一过程仅读取首页。
- 先核验的四组微信+银行材料均因银行侧缺可靠完整抬头而不可用，保留原因 `reliable_header_funding_accounts_unavailable`，不作“无扣款”结论。
- 另一组微信+建行原件在新规则下得到 26 个唯一关联、4 个歧义候选；另一组已具备来源前提但没有同时满足全部严格条件的交易。视觉抽检了两份原件首页，确认微信三要素和交易方式、建行完整抬头与财付通微信支付文字均为明确可见字段。
- 输出脱敏复核：唯一关联记录只含交易 ID、账户/证据引用、日期和金额；未含完整账号、身份证号或微信号。

### 验证

- 执行 `python -m py_compile bankflow_v2\\wechat.py bankflow_v2\\case_accounts.py bankflow_v2\\result_export.py` 与 `python -m unittest tests.test_wechat_alipay_text_fields tests.test_case_accounts tests.test_result_export tests.test_multi_account_merge`，共 37 项通过。
- 按本轮指令未运行全量单元测试和统一回归；支付宝未修改。

## 2026-07-27 微信支付扣款银行流水独立关联

### 范围与实现

- 新增 `wechat_payment_bank_debit_link_candidates`，作为微信消费和其已确认银行账户扣款的独立、可复核观察，不复用 v1C/v1D 的“完整对手账号互相匹配”定义。
- 微信来源必须已有确认记录：姓名、完整身份证号、微信号、稳定账户引用、来源文件 ID 与归属证据引用均非空；银行来源必须精确归属一个可靠完整抬头账户。身份三要素只用于校验，不写入结果 JSON。
- 候选同时要求：微信交易方式的银行卡尾号唯一对应该银行账户、同一自然日、精确同额支出、银行文字同时包含“财付通”和“微信支付”，且微信交易对方的规范化商户组成部分唯一命中银行文字。多候选保留为歧义，不作强制配对。
- 输出仅保留双方交易 ID、微信账户引用、微信归属证据引用、资金账户引用、日期和金额；不回显完整银行卡号、身份证号或微信号。它不表示账户互转、资金来源、闭环、控制关系或案件结论，且不计入 v1C/v1D。
- 支付宝新增固定的待确认观察 `alipay_payment_bank_debit_link_pending_field_confirmation`；在取得支付宝原件字段与对应银行扣款标识前，不建立自动关联。

### 验证与限制

- 以用户提供的建行扣款/微信消费截图结构构造了 395.98 元“小白房子”同日同额样例，并覆盖唯一配对、多银行候选歧义、尾号非唯一拒绝、缺少身份三要素拒绝和支付宝待确认。
- 执行 `python -m py_compile bankflow_v2\\result_export.py` 与 `python -m unittest tests.test_result_export tests.test_wechat_alipay_text_fields tests.test_multi_account_merge`，共 29 项通过。
- 本轮按指令未运行全量单元测试和统一回归；未将截图当作真实双源 PDF 原件验收，待获得可定位的成对来源后再做真实材料验收。

- 真实农业银行对公原件的 `对方账号 / 对方户名 / 对方开户行 / 交易用途`是独立列，账号仅在本单元格内换行；旧 `abc_corp` 优先进入混合文本块解析，只结构化时间、收入、支出和余额，导致 v1C 可靠完整对手账号覆盖为 0。

## 2026-07-19 富滇银行确认字段与文件元数据容器

### 背景

- 富滇确认工作簿 `确认字段!A4:G28` 已完成确认，但前一续接遗漏：21 项状态确认保留原建议，`currency / account_currency / verification_code` 明确排除，电子印章和验真说明按原建议排除。

### 解决方式

- 在 `models.py` 新增：
  - `StatementMetadata`：保存户名、账号、查询起止日期、文件生成时间、分段标识、总页数，以及原始值、来源、置信度和人工复核信息；

  - `get_statement_metadata()`：普通列表安全返回空元数据，避免调用方判断具体列表类型。
- `Transaction` 兼容增加 `source_sequence` 和 `source_fields`；来源专属字段继续共用 `field_sources / field_confidence / manual_review`。
- `fudian.py` 保留真实九列中英文表头，并显式映射：
  - 对方账号、对方户名、摘要描述、备注和商户名称进入标准字段；
  - 商户代码、商户名称及地址原文、二级商户信息、附言和备注剩余结构进入 `source_fields`；
  - 只根据明确标签拆分备注，标签外内容不猜测；中文单元格版面断行只在标准值中消除，原始九列继续保留。
- 从首页表外确定性提取户名、银行账号、查询区间、申请时间、文件分段标识和总页数到 `StatementMetadata`。
- GUI 和命令行 `FileResult` 接入文件元数据；账户名和账号优先使用解析器元数据，现有兜底提取和数字展示保持不变。
- `currency` 不进入逐笔分析字段；`account_currency / verification_code` 及电子印章、验真说明不进入文件元数据。
- 新增 `tests/test_fudian_text_fields.py`，覆盖逐笔标准字段、明确标签拆分、来源专属字段、空值、多行中文、文件元数据、列表兼容和排除字段。

### 验证

- 单元测试：16 项通过。
- `py_compile`：`models.py / fudian.py / pipeline.py / gui_v2.py / main.py / tools/regression.py` 通过。

## 2026-07-25 字段进度总账对账与口径防错

### 问题现象

- 在汇总“未完成文字字段确认与解析”时，直接把人工确认工作簿“来源盘点”中按整家银行或全部版式汇总的 `部分确认 / 部分实现` 计为待完成，错误得出 31 项待办。

### 原因

- 一个来源行可能覆盖多个版式；`部分确认` 表示其他版式仍未外推，不代表已经确认的目标版式未完成。

### 解决方式

- 更新当前人工确认工作簿：同步 24 个已完成来源状态，新增天津农村商业银行个人条目；来源/版式总账为 49 条，其中 42 条已实现、5 条部分实现或未实现、2 条暂缓（缺原件）。

- `PROJECT_STATUS.md` 更新当前实现提交 `03efcb8`、最新验证摘要和冻结项。

### 防错规则

1. 读取“来源盘点”前先确认该行的粒度是“固定目标版式”还是“整家银行/多版式汇总”。
2. 遇到 `部分确认 / 部分实现`，先检索晚于工作簿快照日期的 `chg-*`；只有确认目标版式没有实现记录时，才能列为文字字段待办。
3. 每批实现提交后，必须在同一轮更新工作簿标题日期、来源盘点三状态、执行总览、`PROJECT_STATUS.md` 和续接记录顶部快照；带日期的历史工作簿不回写。
4. 计划或报告不得把聚合来源行直接相加为“未完成字段数”；应按当前目标版式和真实样本验证状态统计。
