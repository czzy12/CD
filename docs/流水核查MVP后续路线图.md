# 流水核查 MVP 后续路线图

更新时间：2026-07-28

## 1. 经营关联模块分级收口

当前经营关联任务固定为：

```text
task_type=business_relevance
prompt_version=business-relevance-mvp-v11
```

经营语义执行前增加独立的经营上下文准入：

1. 优先读取系统中的明确工作介绍、主营业务及业务人员直接描述的具体产品、服务或经营类型，并保留原文、来源字段、来源文件和 `declared_unverified` 状态。
2. 工作单位名称只作辅助；“商贸、科技、实业”等名称不得自动推导主营行业。
3. 只有单位名称、描述宽泛、存在多个无法确定主次的行业或单位与描述明显冲突时，返回 `business_context_confirmation_required`，由人工填写主要经营内容、产品或服务及补充说明。
4. 人工确认与原始描述分别保存；人工确认优先，但不得覆盖或删除原始客户经理描述。
5. 没有明确工作描述且未完成人工确认时，不生成真实AI经营关联调用。

不得重启或推翻已经完成的 v11 确定性边界、非 fail-fast 聚合、缓存、离线重放、固定样本和跨来源统一字段契约。后续验收顺序固定为：

1. 保存通过全量本地测试的 v11 本地检查点。
2. 使用冻结的模型、提示词、案件上下文、硬边界、字段契约和缓存规则运行固定 `development` 50。
3. 不联网离线重放 development 缓存，核对缓存命中、未命中、校验结果和采用状态。
4. development 与离线重放均无关键违规后，由用户另行确认固定 `reserved_acceptance` 50。
5. 两组均无关键违规后，由用户另行确认旧口径337种完整验收：38种本地确定性处理、13种清洗后同义合并、实际286种边界语义送模。
6. 完整验收采用非 fail-fast 聚合；普通单条 `medium / weak / undetermined` 分歧不自动触发调参或全量重跑。

经营关联模块满足以下条件后冻结：

- 确定性硬边界、证据字段和证据定位全部有效。
- 生活类、代码类和金融基础设施类不进入经营结果。
- 明确行业相关交易能够被发现，模糊企业名称和泛化用途保守降级。
- 人工能够回到原交易复核。
- 曹国民4份流水完整验收通过。
- 至少再用一个不同行业、不同来源客户完成小规模代表性抽检。

经营结果仅用于辅助筛选经营线索，不替代人工形成经营真实性、欺诈、包装、准入、通过或拒绝结论。

## 2. 第一版流水核查 MVP 收口顺序

经营关联冻结后，第一版流水核查 MVP 按以下顺序收口：

1. 客户申报工作和经营信息结构化。
2. 下定与购车关键词核查。
3. 主要交易对手及对手集中度。
4. 快进快出和大额资金停留。
5. 余额、结息和月度变化。
6. 敏感交易关键词及上下文。
7. 客户申报信息与流水事实对照。
8. 人工核实问题生成。
9. 可追溯交易证据输出。

v1C、v1D、微信银行扣款扩展和支付宝关联继续冻结；除非第一版 MVP 的必需能力明确依赖，否则不恢复开发。

## 3. 后续独立里程碑：生活轨迹核查 v1

生活轨迹核查只在第一版流水核查 MVP 完整收口后启动。当前阶段不实现生活轨迹提示词、模型调用、测试样本、业务规则或结果 schema。

业务隔离：

- 经营关联判断交易文字与申报工作内容或行业的关系。
- 生活轨迹判断行为类型、地点和持续时间与申报住家、工作地址及主要活动地区的吻合程度。
- 两项任务不共用提示词、强度业务含义、结果 schema 或验收样本。
- 生活消费不得被解释为经营证据。

未来候选信息可包括餐饮、便利店/超市、医疗/药房、打车、停车、加油、充电、高速/ETC、公交/地铁、水电气缴费、酒店和日常服务消费。

保守边界：

- 话费充值通常只能证明日常支出，不能单独证明地点。
- 银行年费不能证明生活地点。
- 全国性连锁品牌不能仅凭品牌名称确定地区。
- 打车记录没有明确城市字段时，只能识别出行，不能证明具体地点。
- 单次异地消费可能是出差或旅游，不能直接否定常住地。
- 未发现某地区交易，不能写成客户没有在该地区生活或工作。

建议处理流程：

```text
交易行为分类
→ 地点候选提取
→ 城市/区县标准化
→ 日期、月份和时段聚合
→ 与住家地址、单位地址、购车地对照
→ 输出支持证据、矛盾候选、偶发活动和不可判断
```

确定性程序优先完成明确消费类别、行政区地名、月份和频次、工作日/休息日、长期/偶发活动及住家/单位/活动地基础对照。AI仅用于模糊商户类型、商户名隐含地点、非标准地名、多地点歧义和规则无法稳定归类的交易。

生活轨迹证据等级需独立设计，至少区分：

- 明确地点且长期持续。
- 明确地点但偶发。
- 仅行为类型、地点未知。
- 地点存在歧义。
- 与申报地区一致候选。
- 与申报地区不一致候选。
- 当前资料不可判断。

输出只允许作为辅助核查事实，不得自动形成虚假住址、虚假单位、挂靠、实际常住地已确认、欺诈、通过或拒绝结论。

## 4. 共享基础设施与任务隔离

未来可以复用标准文字字段、交易时间/金额/方向/来源、原始字段与页行交易ID证据、请求缓存、离线重放和非 fail-fast 批量验收。

不同 AI 任务必须分别具有：

- `task_type`
- 提示词版本
- 输入指纹
- 缓存命名空间与缓存键
- 结果 schema
- 验收样本

任务类型至少区分：

```text
task_type=business_relevance
task_type=life_trajectory
```

新增生活轨迹模块不得改变既有经营关联结果的字段、分类或业务含义。

## 5. 后续企业经营上下文发现模块

当前 MVP 不接入企业信息联网查询。项目成熟后另立模块：

```text
企业名称及统一社会信用代码
→ 查询企业信息源
→ 提取登记范围和外部经营证据
→ AI生成经营方向候选
→ 人工确认
→ 写入正式经营上下文
```

登记经营范围和外部证据只能形成候选，不能自动成为客户实际主营业务；正式经营上下文必须由人工确认。该模块与当前交易经营关联提示词、缓存和结果 schema 分离。

## 6. 跨来源状态表述

必须持续区分：

1. 曹国民4份流水真实语义验收。
2. 统一字段层跨来源本地契约。
3. 其他客户、行业、银行和版式的代表真实样本验收。

当前只能表述为架构上来源无关，并列明已测试的标准字段组合和来源契约；不得根据统一字段设计直接声称所有银行均已支持。
